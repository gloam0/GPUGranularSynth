# GPUGranularSynth

# Pipeline Architecture Plan

Poll controls -> generate audio (GPU) -> copy to audio out, each owned by a thread.

**Control polling**
- "Almost-RT", samples control states at a sub-block cadence.
- Pushes control samples into an SPSC queue to be consumed by the GPU job builder.
- e.g., `ControlSample = { sample_id, control_id, value }`
- De-duplicate adjacent equivalent ControlSamples

**Producer (GPU)**
- "Almost-RT", schedules GPU jobs, each covering `GEN_BLOCK_SIZE` samples
- Consumes slices of control samples from the control queue whose timestamps fall in the range of the current block,
submits them to the GPU as part of the next job spec.
- GPU writes samples directly to the current block SPSC ring/queue shared with the consumer.
- Consumer starts only after ring is pre-filled (i.e., baked-in latency; ring just provides elasticity to protect
against GPU delivery time spikes (e.g., if pre-empted).
- For each job window `[start, start + GEN_BLOCK_SIZE)`:
  - Collect control samples in range, request (wait for) free ring slot, push GPU job `{start_sample, n_samples,
control_evts[], ring_slot}` to GPU job queue.
    - GPU control value policy - sample hold? linterp?
    - linterp is somewhat expensive (esp. across many controls), and I don't see a reason why the control poller would
be unable to poll at a near per-sample basis, thus sample hold is probably the correct policy.

**Consumer / Audio Device**
- Real-time, callback every `DEV_BLOCK_SIZE` samples (JUCE callback).
- Consumes new blocks from the SPSC queue shared with the producer / GPU.


### Notes

All SPSC queues are bounded and pre-allocated (i.e., rings).

**Timing**
- Audio callback provides the source of truth for the time domain - owns a 'total sample count' cursor to be read by
other threads.
- GPU job-spawning thread maintains its own sample cursor, forever chasing the audio callback's sample cursor.

**SPSC Queues**
- Bounded and pre-allocated, i.e., ring buffers or 'ring buffers of buffers'.
- Queue nodes are padded to 64 bytes to avoid constant cache invalidations due to false sharing (e.g., if the write and
read counter members reside on the same cache line, both the producer and consumer observe cache line invalidations
whenever either publishes a read/write).

**GPU reduction**
- If the GPU is expected to generate `GEN_BLOCK_SIZE` samples per partial, across *many* partials. I.e., need to solve
`mix[channel][sample] = sum(i in n_partials) partial_i(channel, sample)`. We can do a parallel reduction (e.g. `p0[] =
p0[] + p1[], ...` -> `p0[] = p0[] + p2[], ...` -> `p0[] = p0[] + p4[], ...` -> `p0[] = p0[] + p8[], ...` ...) which is
O(log2n), but requires `n_partials * GEN_BLOCK_SIZE * n_channels * sizeof(float)` which is potentially humongous, so
we will partition into buckets by thread index:
  - Kernel 1: for each partition, generate samples for that partition's voices, accumulate in shared memory, and write
a partial sum to global memory (buffer per partition)
  - Kernel 2: sum the partitions of partials into the ring, using the process described above

**Underruns**
- The point of the SPSC ring is to protect against underruns by 'baking in' some latency such that there is a queue
of pre-generated buffers at any time to protect against GPU usage spikes.
- In the case of underruns, we output the 'last good' sample buffer with the hope to make the resulting audio glitches
more subtle than outputting zeros (or junk).

**Block sizes**
`GEN_BLOCK_SIZE` and `DEV_BLOCK_SIZE` may be different values, such that if kernel launch costs are high,
`GEN_BLOCK_SIZE` may be increased ot amortize launch overhead, while the audio device's block size remains smaller (with
the tradeoff of greater latency `1000 * GEN_BLOCK_SIZE * RING_SIZE / SAMPLE_RATE` milliseconds)
